# 構成から本文までの動作確認

構成を検査してから本文を書く工程を7件で実行し、修正後の本文は全件で親の意味・構成の検査とtextlintを通過した。構成は4件、本文は1件を差し戻した。構成案を作らせるだけでは、重複や見出しの問題は消えなかった。

## 条件

執筆は既存ベンチマークと同じ `gpt-5.6-luna`、推論量 `low`、Codex CLI 0.150.1で実行した。親の検査はこの変更を担当したGPT-6が行った。親の呼び出し条件は執筆モデルと同一ではない。

対象は3cb114cを親とする変更中のスキルである。[実行記録](evidence.json)に参照ファイルの全文とSHA-256、原依頼、構成案、親の判定、本文、修正指摘、生成量を保存した。構成と本文は別のモデル呼び出しとし、親が実際の構成案を読んで合格にするまで本文を生成しなかった。

既存の `benchmark.mjs` のモデル呼び出しと測定処理を、一時スクリプトから利用した。スクリプトも実行記録に収めた。本文の呼び出し前に、合格判定と最新の構成案のハッシュが一致するか確認する。構成のない状態での本文生成は、モデル呼び出し前に停止した。

生成側には原依頼、スキル、担当工程を渡した。構成の初稿へ判定基準や望ましい見出しを追加していない。修正時には、親が実物から見つけた指摘を渡した。本文へは検査済みの構成を渡した。

## 限界

これは親の検査を挟む工程の動作確認であり、既存の一括生成ベンチマークの点数とは比較しない。スキルの自動発火や、工程の切り替えを実行者だけで守れるかは測定していない。設計と障害記録は各2反復に限られ、未知の題材への効果は未検証である。本文から構成へ戻る分岐、昇格、上限到達も今回の実行では発生していない。

実行者の形式説明には、一文を一段落と呼ぶなどの不正確さが残った。部分修正の構成案にも、見出しがないと手順を扱えないという誤説明があった。親は形式説明をそのまま信用せず、実際の本文とユーザーの変更範囲から判断した。

構成を生成した直後の端末表示にある「0 lint messages」は、構成のlint検査結果ではない。静的検査は本文にだけ実行した。追加ケースの文書分類名を誤った試行はモデル呼び出し前に停止し、分類名を訂正して実行した。
