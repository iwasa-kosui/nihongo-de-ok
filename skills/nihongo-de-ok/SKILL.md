# 日本語でおｋ

読者が判断・実装・操作できる最短の文書を書く。文字数を減らすために、事実、条件、根拠、例外、責任の所在を落とさない。

## 1. 文書の役割を決める

[文書分類](references/document-types.md)から該当する行だけ読む。執筆前に次の情報を短く決める。これは作業用メモであり、成果物へ必ず挿入する項目ではない。

- 種別と区分: `prd` / `design-doc` / `adr` / `rfc` / `stock` / `flow` / `record`
- 読者: 誰が、何を知っているか。
- 目的: 読後に何を判断・実行できるか。
- 目的外: この文書で管理しないこと。
- 根拠: 参照する資料と、まだ分からないこと。

対応範囲を先に決める。必要性の検討だけなら、新規文書が不要という判断で止められる。既存の正本で足り、新規文書を求められていなければ参照と補足だけにする。指定箇所の修正はその範囲を守り、文書全体を組み替えない。明示された作成依頼は省略しない。

資料を確認してから形式を選ぶ。重大な不足だけ質問し、未確認の数値、承認、仕様を補わない。確認待ちでも書ける部分は進める。組織の呼び名が表になければ、この5点で役割を定める。

ADR では [判断と結果の書き方](references/document-shapes.md#adr-の判断と結果を残す)も読む。背景・決定・結果を基本とし、未決定事項を必須の節にしない。結果の段落にも未決定事項を混ぜない。判断を左右する不確実性は前提や採用条件として残し、後続の詳細設計と区別する。

## 2. 構成を立てて検査する

本文を書く前に、各節の見出し候補（なしも可）、答える問い、含める情報と根拠を短く整理する。どの節が何を受け持つかを検査できる構成案にし、説明文はまだ書かない。指定箇所だけの修正では、既存の構成と変更箇所の役割を確認する。

まず文書が伝える主張を一文で書き、それを冒頭に置く。節はこの主張への従属関係で決まる。主張を決めずに節を並べると、結論が末尾に沈み、主張を担保する論点が並列に見え、同じ根拠が複数の節に散る。

構成のラダーは、次の順に検討して最初に成立する形で止める。

| ステップ | 構成 | 必要になる条件 |
|---|---|---|
| 0 | 見出しなし | 主張と根拠を一つの問いで扱える |
| 1 | 並列の節 | 主張とは別に独立して参照する問いがある |
| 2 | 親子の節 | 主張を担保する下位の問いがある |

節に名前を付けられるだけでは分けない。親子の構成も、下位の問いが必要な部分にだけ使う。短い案内の構成案は、問いと含める情報を一文で示せばよい。ユーザーが指定した構成・見出し・書式と、他の節から参照されている見出し名・識別子は、階層を組み替えても保つ。

親は [文書全体の構成を決める](references/japanese.md#文書全体の構成を決める) で構成案を点検し、節を削除・統合しても情報を保てるなら構成を直す。

構成案と、親の合格または指摘を作業記録に残す。構成が合格するまで本文の執筆を始めない。合格判定は親が行い、通常の構成判断のためにユーザーの確認を待たない。委譲できない場合も、執筆者自身が構成案を点検してから本文を書く。検査していない構成を合格済みと報告しない。

## 3. 各節に合う形で執筆する

[委譲手順](references/delegation.md)に従い、合格した構成案を渡して本文を依頼する。各節はその問いに答え、割り当てた事実・条件・例外を残す。他の節が受け持つ説明を繰り返さない。見出しのない文書は全体を一つの単位として扱う。

本文のラダーも、各節で最初に成立する形を選ぶ。構成のステップ番号とは別に扱う。

| ステップ | 本文の形 | 必要になる条件 |
|---|---|---|
| 0 | 一文 | 必要情報と関係を一文で伝えられる |
| 1 | 一段落 | 結論に理由や条件を添える必要がある |
| 2 | 複数段落 | 同じ問いに複数の説明が必要 |
| 3 | 小節 | 独立して参照する下位の問いがある |

比較・対応なら表、順序が必要な操作なら手順、短い名称や確認事項なら列挙を選べる。これらは節の役割に応じた分岐であり、全ての節を同じ形式にそろえない。背景は検討の前提、設計は処理と条件、影響は採用による変化というように、その節の問いから判断する。詳しい情報の選択は [PRD・設計・判断の書き分け](references/document-shapes.md) を必要なときだけ読む。

ADR の理由、PRD の受入条件、Runbook の停止条件などが欠けるなら、短くても不合格とする。小節や新しい論点が必要になったら、該当部分の構成案を直して再検査してから書く。細分化することだけを目的にラダーを繰り返さない。

箇条書きと段落の選択は [文章のまとまりを判断する](references/japanese.md#文章のまとまりを判断する) に従い、必要な構成変更を再検査する。

表は見出しを含め全セルを60文字以内にする。1セルでも61文字以上ある表は使わない。[表の一覧性を保つ](references/japanese.md#表の一覧性を保つ) に従い、詳細は表の外へ移し、条件や例外を削って文字数を合わせない。

## 4. 全文をつないで点検する

各節をつなぎ、構成案の問いと分担を本文に照らして再検査する。執筆によって分かった重複や不足は、影響する節の構成と本文へ戻して直す。構成の合格だけで本文まで合格としない。

原資料に照らし、事実・提案・未決定を分ける。数値、条件、否定、例外を保ち、もっともらしい仕様を補わない。`stock`（PRD、Design Doc、RFC、ADR を含む）に進捗、PR番号、Jira課題IDを入れない。追跡は作業文書側から設計・判断を参照する。ADR の採用・廃止・置換、判断日、別 ADR への参照や、仕様の業務状態は残す。`flow` と `record` に必要な日付、担当、時系列、課題参照を機械的に削除しない。

語と文の意味、情報量と構造、見出しと論旨の対応は [日本語の基準](references/japanese.md) で点検する。辞書に載っていない表現にも同じ基準を適用し、見出しだけ短くして構成の点検を済ませない。

## 5. textlint で検査して届ける

この `SKILL.md` があるディレクトリをスキルルートとする。初回だけルートで `npm ci` を実行する。検査コマンドでは実際の絶対パスを使う。

```sh
node <スキルルート>/scripts/lint.mjs --type design-doc <成果物の絶対パス.md>
```

`--type` は必須。種類が混在する複数文書は種類ごとに実行する。構成・意味の指摘と lint の指摘をまとめて実行者に返し、文意を確認して直す。最終変更後に再検査する。`allow` の指定と除外の範囲は [`allow` 設定](references/lint.md#allow-設定) に従う。合格のためにルールを全体で無効にしたり、問題文をコード・引用へ逃がしたりしない。

textlint は繰り返し検出できる語法・文型を検査し、執筆者は文脈での意味と事実を点検する。検出漏れは [静的検査との分担](references/japanese.md#静的検査との分担) に従い、語を辞書に足すだけで解決したことにしない。意味の点検と textlint の両方が通って初めて完了とする。修正・昇格の上限に達したら、残る問題を明記して草稿として返す。依存取得や検査に失敗した場合も未検証と伝える。

成果物は本文かファイルへのリンクで返す。構成・本文に選んだ形と検査結果は本文外に一行で添える。構成案、判定記録、モデルの実行記録、lint結果を文書本文に混ぜない。執筆依頼だけで送信・公開・Git操作を行わない。

設計の参考: [ponytail](https://github.com/DietrichGebert/ponytail/blob/main/skills/ponytail/SKILL.md) の「成立する最小の手段で止める」を文書に応用した。常時有効化やコード専用の出力制約は引き継がない。
