# 日本語の基準

読者が、誰が何をするのか、何がどう変わるのかを補わずに読める文章にする。短さは、必要な意味を保ったうえで求める。

## 文ごとに判断する

| 観点 | 確かめること | 直し方 |
|---|---|---|
| 根拠 | 事実・提案・未決定のどれか。資料と一致するか | 数値・条件・例外を保ち、推測は提案として区別する |
| 語の選択 | 読者になじみがあり、実際の動作や変化を表すか | 借り物の大きな言葉を、行ったこと・起きたことに戻す |
| 専門語 | 日常語に換えると必要な意味の区別が失われるか | 必要なら専門語を使い、読者が知らなければ初出で説明する |
| 主体と対象 | 誰が何に対して何をするのかが一意に読めるか | 主体・対象・動詞を明確にする |
| 評価と条件 | 良し悪しや実施条件を読者が判断できるか | 形容詞・副詞だけで済ませず、範囲・比較対象・判断基準を書く |
| 名詞の関係 | 長い名前の中で、各要素がどう関係するか | 利用者・対象・動作の関係を説明する |
| 必要性 | 消すと判断・操作・理解に必要な情報が失われるか | 情報を増やさない前置き、言い直し、重複を削る |

辞書にない語にもこの基準を使う。説明のない抽象語を別の抽象語に換えても、改善にはならない。具体化に必要な事実が資料にない場合は確認し、数値や条件を作らない。

主語を全ての文に足す必要はない。段落や手順で担当が明らかなら省略する。主体が変わる、指示語の参照先が複数ある、受け身で担当が分からない場合は具体名を書く。指示語、受け身、動作の名詞は、具体的な主体・対象・動詞に戻して関係を明らかにする。

長い名前は、誰が使う何で、何をするのかを説明する。既存の名称があれば使う。

正式名称は勝手に変えない。専門語を避けて説明が長くなったり不正確になったりするなら、その語を使う。外来語か漢語かという形だけでは決めない。

「本質的」「根本的」などの評価は、本文が扱う範囲や根拠に見合うか確かめる。「羅針盤」「旅」のような比喩や、「代償」のように損失を強調する語も、その意味が必要な場合に限る。日常の費用や運用負担なら、費用・手間・制約を具体的に書く。日本語での表現への批評として、[もとやまによる業務文書の批評](https://note.com/yusuke_motoyama/n/n2a1218636f56)や[もりうちゆいによる定型表現の批評](https://note.com/yui_coach/n/n29e0873ef8dd)も参考にする。個人の批評を、日本語コミュニティ全体の合意や、AI が書いた証拠として扱わない。

## 語義と語の組み合わせを確かめる

原語の辞書的な訳を当てる前に、その文で何を指しているか確かめる。手順の step を「段」とするのは、階段の意味を別の文脈へ持ち込む誤りである。「ステップ」「手順」など、読者が操作の順序として読める語を選ぶ。同様に、データの field を「畑」とせず「フィールド」や「項目」とする。文字数の少なさや漢字であることを、自然な日本語の根拠にしない。物理的な「段」、農地の「畑」、「段階」「段落」など、文脈に合う用法は保つ。

名詞だけでなく、結び付く助詞と述語も読む。「価値を解き放つ」は、その価値を受ける相手と、何ができるようになるかが分からない。「価値は解き放たれた」「価値の解放」と形を変えても、この不足は残る。短い漢語、カタカナ、別の抽象語への置換で済ませず、原資料が示す対象と変化を書く。原資料に説明がなければ、補わず確認する。

助詞を足しただけでも、関係の説明にはならない。「顧客体験向上プラットフォーム」を「顧客の体験の向上プラットフォーム」にしても、利用者が何をできる仕組みかは分からない。一方、担当・対象・操作が明確な文まで、同じ名詞があるという理由で削らない。「適切な対応を行う」も「適切に対応する」も、何を基準に何をするか確かめる対象になる。丁寧語・過去形・否定形に変わっても判断基準は同じであり、修正時には時制と否定を保つ。

## 文書全体の構成を決める

構成案の「答える問い」と「含める情報」を読み、読者が知りたいことと、判断に必要な情報の関係から節を組む。必要情報の一覧を、そのまま同じ階層の見出しにしない。同じ階層の節はそれぞれ別の問いを受け持ち、前提が分からないまま判断を求められない順序に置く。結論を先に示す場合も、根拠をたどれるようにする。ユーザーが指定した構成や見出しは守る。

### 包含関係から節をまとめる

見出しは節全体を代表する名前であり、本文の話題の一覧ではない。目的や範囲が、なぜこの検討が必要かを説明する一部なら、「背景と目的」「背景と範囲」は「背景」でよい。目的や範囲の記述は本文に残す。「結果」が利点や負担を含む場合の「結果と代償」も、全体とその一部を並べている。

包含関係は語だけで固定せず、その文書での情報の役割から判断する。成功条件を目的と照合する、対象内外を実装や受入判定で繰り返し参照するなど、独立して探す必要があれば「目的」「範囲」を分ける。「背景」を何でも入れる節にせず、同じ説明を複数の節に重ねない。「結果と未決定事項」のように役割が違う情報は、それぞれ必要な場所へ分ける。「在庫と注文の更新」のように二つの対象の関係を扱う見出しは保てる。「と」の有無や文字数で一律に決めない。

例えば「背景」の構成案に処理方式と結果提示の遅延を置き、「設計」に同じ処理方式、「影響」に同じ遅延を置いたなら、節名を短くするだけでは重複が残る。処理方式は設計、遅延は影響へ集約し、背景に独自の前提や理由が残らなければ、その節を省く。独立した役割がある情報まで一つの節へ押し込まない。

### 意味を増やさない修飾を削る

「改善課題」は通常「課題」でよい。課題には改善・解決すべきことという意味があり、「改善」を足しても対象や性質を区別できないためである。これは節の包含関係とは別に、修飾語が情報を増やすかという判断であり、本文の情報を移す必要はない。

修飾語を外しても指す内容が変わらないかを確かめる。「運用上の課題」が技術や費用の課題と区別する役割を持つなら、その限定は残す。正式名称や指定された分類名も保ち、漢字の連結や「改善」という語だけを理由に削らない。原資料に語が現れるだけでは、変更できない正式名称や指定見出しとは扱わない。

## 見出しと論旨を照合する

構成案の合格後も、執筆した本文を各節の問いと照合する。背景に設計の詳しい説明が入り、影響に同じ仕組みが再登場するなど、節の分担が変わっていれば、情報の置き場所を直す。新しい問いや小節が必要なら、該当部分の構成を再検査する。

見出しで掲げた問いに、本文が答えているかを確かめる。比較の基準を示したら、各案の分析と結論もその基準に照らす。「運用負担の比較」という節に価格しか書かれていないなら、運用負担の根拠を確認するか、資料で答えられる範囲に見出しと結論を直す。見出しを埋めるために説明を創作しない。

比喩が暗示する因果関係や比較を、本文の事実で説明できるか確かめる。例えば、相関しか分からない二つの現象を「病気と症状」に例えると、原因まで判明しているように読める。対応を説明できなければ、実際に分かっている関係を書く。大きな問いを掲げる前置きや結論の言い直しも、事実・条件・理由・判断を増やさなければ削る。

この点検は、todesking の[「AIっぽさはどこからくるのか」](https://zenn.dev/todesking/scraps/da4b4a01cec42b)を参考にした。記事は比喩と論旨の不一致、掲げた基準と後続の分析の不一致を指摘している。本スキルでは文章の内容を点検する基準として使い、AI による執筆を見分ける証拠とは扱わない。引用や専門語まで削ったり、語尾や記号を機械的に変えたりして、人間らしい外見だけを作らない。

## 文章のまとまりを判断する

文章で説明する箇条書きが5項目以上になる場合は、関連する内容を意味のまとまりごとの段落にまとめる。見出しは、独立して参照する問いがある場合だけ付ける。項目数を見出しの必要性の根拠にしない。項目が短くても、説明文を並べているなら対象になる。4項目以下でも、一項目が長い場合や因果・条件・対比を追う必要がある場合は段落を使う。

見出しは論点を示し、段落はその中の結論と理由、条件と結果などの関係を伝える。一項目ずつ見出しに変えたり、4項目ずつ別のリストに割ったり、入れ子に移したりして数だけ減らさない。全項目を一つの長い段落に詰め込まず、必要な情報を保って意味のまとまりで分ける。

短い名称・値・選択肢の列挙、個別に確認するチェックリスト、実行順序が必要な番号付き手順は、5項目以上でもその形を保てる。ただし、説明文に番号を付けただけなら手順ではない。項目どうしの関係で判断する。ユーザーが箇条書きや既存形式の維持を指定した場合は、その指定を守る。

### 組み替える前

- 申請者は申請フォームから利用申請を送る。
- チーム責任者が申請内容を審査する。
- 必須項目が不足していれば、責任者は申請者へ差し戻す。
- 審査結果は申請者にメールで届く。
- 却下された場合、申請者は理由を確認してから再申請する。

### 組み替えた後

#### 申請と審査

申請者は申請フォームから利用申請を送る。チーム責任者が内容を審査し、必須項目が不足していれば申請者へ差し戻す。

#### 結果の確認と再申請

審査結果は申請者にメールで届く。却下された場合は理由を確認してから再申請する。

## 表の一覧性を保つ

表は短い項目や値の違い、対応関係を見渡すために使う。見出しセルも含め、1セルでも61文字以上ある表は禁止する。全セルを60文字以内に収めても、説明を読み込まないと比較できない表は見出しと段落に組み替える。

文字数は表示上の文字で数える。句読点、数字、内部の空白、リンクの表示文、インラインコード、画像の代替文を含める。セル前後の余白、Markdownの装飾記号、リンク先URLは含めない。結合文字や複数コードポイントの絵文字は、表示上の1文字として数える。セル内で改行しても、セル全体の文字数で判断する。

長い説明は表の外へ移し、表には比較に必要な短い要点だけ残す。表を求められた場合も同じ上限を守る。意味のないセル分割、独自の略語、条件や例外の削除で数だけ減らさない。列を増やすと生じる空欄を、資料にない値で埋めない。表をやめた結果、文章の箇条書きを大量に並べることも避ける。

例えば権限の比較表なら、表には「編集者」「編集可」などの対応だけを残し、編集できる範囲や例外は「編集権限」の節で説明する。詳細との対応が分からなくなるなら、表全体を論点ごとの見出しと段落へ変える。

## 書き換え例

| 書き換え前 | 書き換え後 | 直したこと |
|---|---|---|
| 既存資産をレバレッジする | 既存の認証基盤を使う | 使うものと動作 |
| シームレスな体験を提供する | 再ログインせずに請求画面へ移れる | 利用者の操作 |
| 対応品質の向上を推進する | 問い合わせ窓口を一つにする | 実際に変えること |
| 適切に対応する | API は認証に失敗したら401を返す | 条件、主体、結果 |
| それを実施する | 当番がバックアップから復元する | 指示語の対象と担当 |
| 高速な検索を実現する | 同じデータで検索時間が2秒から0.5秒に減る | 比較対象と結果 |
| 部門横断意思決定支援基盤を構築する | 各部門の責任者が売上を比較できるようにする | 利用者、データ、用途 |
| 代償として DB の保存量が増える | DB の保存量が増える | 決定による負担 |

これらは対応する根拠がある場合の例であり、決まった置換先ではない。例の機能や数値を転用しない。短くするために対象や条件を広げたり、否定や例外を落としたりしない。

## 静的検査との分担

textlint は、再現できる語法・文型の問題を繰り返し検出し、執筆者が意味を点検する箇所を示す。助詞の重複や二重否定は既存の日本語ルールを使う。独自の文章ルールは、文を形態素に分け、語の基本形・品詞と助詞の接続から、活用や名詞化で形が変わる表現も検査する。名詞の連結は、目的・抽象的な変化・仕組みの組み合わせを見る。検出例の一覧だけをスキルの判断基準にしない。

文脈での語義、前の文で説明された指示語、事実の正しさ、節の包含関係、修飾の必要性、見出し・判断基準と本文の対応、比喩の妥当性は執筆者が点検する。形態素解析は係り受けや意味の正しさを保証しない。見出しの例を禁止語に登録したり、一律に置換したりしない。箇条書きも役割で判断し、項目数だけを数えて一律に禁止しない。

`table-cell-length` は Markdown の表で61文字以上のセルを検出する。原文を保存する引用ブロックとコード例は検査対象外とする。HTML や他形式の表にも同じ上限を適用し、執筆者が確認する。文字数の検査に通っても、表の一覧性は本文を読んで点検する。

指摘には直す観点を添え、文脈を確認して修正する。自動置換は行わない。必要な専門用語や正式名称は、文章ルールの `allow` に文字列で指定する。その文字列と一致する範囲だけを除外し、同じ段落の他の表現は検査する。

文章ルールは通常本文とリンクの表示文を対象にする。コード、URL、引用ブロックは原文を保存するため対象外とする。作業追跡のルールはリンク先とインラインコードも検査する。引用やコードへ移して検査を回避しない。

基準を更新するときは、報告された語が上のどの問題に当たるかを先に決める。再現する検出漏れには、助詞の違い、丁寧語・過去・否定などの活用、動詞と名詞の言い換え、修飾語の挿入を含めて回帰テストを書く。同時に、似た表層でも意味や接続が異なる正しい用法を確認する。助詞を全て消して照合したり、任意の文字列を飛び越す正規表現で別の文を結び付けたりしない。

強調やリンクの表示文にまたがっても検査し、引用・コード・URLや文・表セルの境界を越えた誤検出を防ぐ。指摘範囲と用語の例外範囲も検証する。スキルの改修であれば実装と配布版を更新し、通常の執筆依頼であれば意味を直して未対応の検出例を本文外に伝える。執筆依頼だけでスキルの実装変更まで行う必要はない。

既存の日本語検査には [preset-japanese](https://github.com/textlint-ja/textlint-rule-preset-japanese) を使う。カスタム検査は [textlint Rule API](https://textlint.org/docs/rule/) に従う。
