# 日本語の基準

短さは、読者が意味を補わなくて済む範囲で求める。日本語として普通の技術用語は残し、その読者が知らない語は初出で説明する。

## 書き換えの判断

| 避ける書き方 | 書き換え例 | 確認すること |
|---|---|---|
| 不具合を観測した | 不具合を確認した | 実際に何を確かめたか |
| 応答時間を観測する | 応答時間を計測する | 数値を測ったのか、動作を確かめたのか |
| 既存基盤をレバレッジする | 既存の認証基盤を使う | 何を使うか |
| シームレスな体験を提供する | 再ログインせずに請求画面へ移れる | 利用者の操作がどう変わるか |
| アクショナブルな知見を得る | 解約理由を調べ、改善する機能を決める | 調査後に誰が何を決めるか |
| 価値創出最大化基盤を構築する | 営業担当が商談履歴を検索できるようにする | 名前を作る前に、利用者と機能を説明できるか |
| 適切に対応する | API は認証に失敗したら401を返す | 条件、主体、動作、結果 |
| これを実施する | 運用担当がバックアップから復元する | 指示語が指す対象 |
| 必要に応じて対応する | 失敗率が5%を超えたら、当番が配信を停止する | 判断基準と担当 |
| AではなくBです、という枠組みで捉える | Bとする。理由は…… | 対比が判断の説明に必要か |

これらは文脈を仮定した例であり、辞書置換で生成する正解ではない。例の数値や仕様を根拠なしに転用しない。

日常の確認や調査を「観測」と呼ばない。文脈に応じて「確認」「計測」「調査」「検知」などに書き分ける。textlint は言い換えを促し、自動置換はしない。「可観測性」のような技術用語は残す。それ以外でも専門分野の用語として必要なら、その理由を確認して `allow` に「観測」を指定する。

「オーケストレーション」「可観測性」「依存性注入」「提供する」などを単語だけで禁止しない。技術的な意味が必要なら使う。名詞を連結して新しい名前を作るより、既存の名前と動詞で関係を書く。正式な名称は勝手に変えず、必要なら短い説明を添える。

## 主体と対象

主語を全ての文に足す必要はない。段落や手順の担当が明らかなら省略してよい。次の場合は具体名を書く。

- 動作の主体が前の文から変わる。
- 「これ」「それ」「本対応」の参照先が複数ある。
- 受け身で、誰が操作・承認するのか分からない。
- 「対応」「実施」「推進」だけで、結果の状態が分からない。

一文に複数の条件や例外があるときは分ける。ただし条件を離しすぎて適用範囲を変えない。箇条書きは並列・順序・比較に使う。見出しに抽象名を重ねず、内容を表す語を書く。

## 静的検査の範囲

同梱ルールは、直訳調・造語・曖昧な動作の有限パターンと、ストック文書への作業追跡情報の混入を検査する。意味を保証する日本語解析器ではない。辞書にない造語、離れた文の指示関係、複数の解釈がある主語・目的語は、人または執筆エージェントが点検する。

意味のある技術語、短い文、主語の省略まで文字数や品詞だけで一律に落とさない。検出時は置換の候補を読み、原資料と突き合わせて書き直す。自動修正は行わない。

カスタムの文章ルールは通常本文とリンクの表示文を対象にする。コード、URL、引用ブロックは原文を保存するため対象外とする。作業追跡のルールはリンク先とインラインコードも検査する。引用やコードへ移して検査を回避しない。

既存の日本語検査には [preset-japanese](https://github.com/textlint-ja/textlint-rule-preset-japanese) を使う。カスタム検査は [textlint Rule API](https://textlint.org/docs/rule/) に従う。プリセット由来の指摘と本スキルの辞書による指摘は、ルール名で区別できる。
