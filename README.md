# 日本語でおｋ

メモや草稿を、読んだ人が次の判断・行動に使える文書へ。日本語の業務・技術文書を執筆・推敲するエージェントスキルです。

設計の理由、仕様の例外、手順の停止条件を残しながら、読み手に必要な長さへ整えます。PRD、Design Doc、ADRから進捗報告、障害記録まで、文書の役割に合わせて書き分けます。

[導入する](#導入) · [依頼と成果物を見る](#こんなふうに使えます) · [スキル有無を読み比べる](#実際の出力を読み比べる)

## こんなふうに使えます

### 曖昧な仕様を、利用者に説明できる文章に

草稿と確定事項を渡して、CS担当が通常の動作と例外を説明できる文章にします。

**依頼**

```text
$nihongo-de-ok CS担当向けの仕様説明を推敲して。

草稿:
「既存基盤をレバレッジし、シームレスな体験を提供する。
価値創出最大化基盤により適切に対応する。」

確定事項:
利用者は既存の認証で請求画面へ移れる。再ログインは不要。
認証の有効期限が切れている場合だけログイン画面を表示する。
草稿中の造語は正式名称ではない。
```

**成果物**

> 利用者は既存の認証情報で請求画面へ移動できます。再ログインは不要です。ただし、認証の有効期限が切れている場合はログイン画面を表示します。

利用者に起きることを具体化し、認証切れの例外も残しています。[本文とレビューを読む](benchmarks/results/2026-09-06-main-fb6fd0b/document-review/comparisons/plain-japanese.1.md)。

### 作業メモから、判断の理由と影響が分かるADRに

採用した方式、採らなかった理由、利用者への影響を、将来の保守者が読める形にまとめます。

**依頼**

```text
$nihongo-de-ok 将来の保守者向けにADRを書いて。

2026-08-20に採用した判断。
請求書のPDF生成はキューで処理し、APIは受付IDを返す。
同期生成は最大45秒かかって接続が切れるため採らない。
非同期では利用者が完成まで待つ必要がある。
再試行の上限は未決定。
作業メモには BILL-218、PR #106、進捗70% とある。
```

**成果物から背景・決定・結果を抜粋**

> ## 背景
>
> 請求書のPDF生成は最大45秒かかり、同期処理ではAPI接続が切れる。
>
> ## 決定
>
> 請求書のPDF生成をキューで処理する。APIは生成要求を受け付けた時点で受付IDを返す。同期生成は採用しない。
>
> ## 結果
>
> APIの接続を生成完了まで維持する必要がなくなる。一方、利用者はPDFの完成まで待つ必要がある。

採用理由と引き換えに生じる待ち時間を残しています。作業チケットや進捗は本文に含めず、資料にない照会方式も追加していません。[ADRの全文とレビューを読む](benchmarks/results/2026-09-06-main-fb6fd0b/document-review/comparisons/adr-boundary.2.md)。

### 手順書の一文だけを、当番が動ける表現に

既存の文書では、直したい範囲を指定できます。

**依頼**

```text
$nihongo-de-ok 次の手順の末尾「必要に応じて対応する。」だけを、
確定事項「失敗率が7%を超えたら当番が配信を停止する。」に直して。
他の部分は変えず、改稿後の全文を返して。

# 配信の確認

当番は監視画面を開く。
成功件数と失敗件数を確認する。
必要に応じて対応する。
```

**成果物の修正箇所**

> 失敗率が7%を超えたら当番が配信を停止する。

条件・担当・操作を一文で示し、タイトルと他の行は維持しています。[改稿後の全文とレビューを読む](benchmarks/results/2026-09-06-main-fb6fd0b/document-review/comparisons/surgical-edit.1.md)。

成果物例は、ベンチマークで保存したスキルありの出力から引用しています。依頼文は、手元で試せるようにスキルの呼び出しを付けて整えています。

## 導入

Node.js 22 以降が必要です。リポジトリ全体が一つのスキルなので、Codex の個人用スキル配置先へ clone し、依存関係をインストールします。

```sh
git clone https://github.com/iwasa-kosui/nihongo-de-ok.git ~/.codex/skills/nihongo-de-ok
cd ~/.codex/skills/nihongo-de-ok
npm ci
```

`CODEX_HOME` を変更している場合は、その配下の `skills/nihongo-de-ok` に置いてください。他のエージェントでも、利用するエージェントのスキル配置先へリポジトリ全体を置き、`SKILL.md` を読み込んでください。文章生成はホストのエージェント機能を使い、このリポジトリから推論 API は呼びません。

## 手元の資料で試す

読者と、その人が読後に何を判断・実行できればよいかを伝え、資料を添えます。新しく書く場合も、既存文書を直す場合も使えます。

たとえば、顧客調査メモからPRDを起こすなら、次のように依頼します。

```text
$nihongo-de-ok 次の顧客調査メモから、開発とQA向けのPRDを書いて。
何を誰のために作るかと、受入条件を確認できる文書にして。
確認できた要求と、追加確認が必要な点を分けて。

（ここに調査メモを貼る）
```

Design Docなら実現方式と不採用案の理由、進捗報告なら完了・次の作業・判断待ちの点を伝えます。対応する文書と用途は[文書分類](references/document-types.md)で確認できます。

## 書いた文書を検査する

スキルは執筆後に意味を確認し、textlintで言い回しや構成を検査します。手元の文書をCLIで検査するときは、スキルルートから対象文書の区分を `--type` で指定します。

```sh
node scripts/lint.mjs --type stock README.md
```

全ての区分、ルール、設定、終了コードは [CLIと静的検査の詳細](references/lint.md) を参照してください。

静的検査は既知の言い回しや表の長さを検出しますが、日本語の意味、事実の正しさ、文書の役割は保証しません。[日本語の基準](references/japanese.md)に沿った確認と、根拠資料との照合も必要です。
